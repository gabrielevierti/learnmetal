Piattaforme Apple

visionOS#

Su Apple Vision Pro la maggior parte delle app disegna con RealityKit.
Quando vuoi un renderer tuo, per un game engine o una visualizzazione, disegni contenuti completamente immersivi con Metal attraverso un framework chiamato Compositor Services.
I tuoi shader e le tue pipeline sono quelli di questo libro.
Di nuovo c'è tutto ciò che sta intorno al frame: gli occhi sono due, la camera è la testa di una persona e la scadenza è rigida.

Che cosa cambia#

  • Due viste.
    Ogni frame viene disegnato una volta per occhio, con una matrice view e una di proiezione diverse per ciascuno.
  • La camera non è tua.
    La matrice view arriva dalla posizione tracciata del visore, attraverso ARKit.
  • Il ciclo dei frame non è tuo.
    Non ci sono né MTKView né display link.
    Compositor Services ti dà i frame e ti dice quando cominciare a lavorare su ciascuno.
  • Il sistema riproietta.
    Appena prima della visualizzazione il sistema deforma la tua immagine per farla corrispondere all'ultima posizione della testa.
    Per farlo ha bisogno del tuo depth buffer, quindi la profondità deve essere corretta per ogni pixel che disegni.
  • Foveation.
    Il visore disegna la periferia a una risoluzione più bassa.
    Lo ottieni quasi gratis, ma cambia il modo in cui funzionano i viewport e il post-processing.
  • La latenza è comfort.
    Qui un frame in ritardo non è un piccolo scatto.
    Punta alla frequenza dello schermo, 90 frame al secondo o più, a ogni frame.

L'app e il layer#

Il punto d'ingresso è SwiftUI.
Un ImmersiveSpace il cui contenuto è un CompositorLayer ti consegna un LayerRenderer, l'oggetto che sostituisce la vista.
Da lì avvia un thread di rendering dedicato; non disegnare mai sul thread principale.

import SwiftUI
import CompositorServices

struct LayerConfiguration: CompositorLayerConfiguration {
    func makeConfiguration(capabilities: LayerRenderer.Capabilities,
                           configuration: inout LayerRenderer.Configuration) {
        let foveation = capabilities.supportsFoveation
        let layouts = capabilities.supportedLayouts(options: foveation ? [.foveationEnabled] : [])

        configuration.layout = layouts.contains(.layered) ? .layered : .dedicated
        configuration.isFoveationEnabled = foveation
        configuration.colorFormat = .rgba16Float          // HDR
        configuration.depthFormat = .depth32Float
    }
}

@main
struct ImmersiveApp: App {
    var body: some Scene {
        WindowGroup { ContentView() }                      // a window with a button that opens the space

        ImmersiveSpace(id: "Scene") {
            CompositorLayer(configuration: LayerConfiguration()) { layerRenderer in
                let renderer = Renderer(layerRenderer)
                let thread = Thread { renderer.renderLoop() }
                thread.name = "Render Thread"
                thread.start()
            }
        }
    }
}

Il punto d'ingresso di un'app visionOS è sempre SwiftUI, quindi in un progetto C++ resta un piccolo file Swift come quello qui sotto.
Tutto il resto può essere C++: Compositor Services ha un'API C (cp_layer_renderer_t, cp_frame_t, cp_drawable_t), che è quella usata dai motori.
La closure Swift passa il layer renderer a una funzione C che avvia il tuo thread di rendering.

ImmersiveSpace(id: "Scene") {
    CompositorLayer(configuration: LayerConfiguration()) { layerRenderer in
        engine_start(layerRenderer)          // a C function, declared in the bridging header
    }
}

Su visionOS non c'è GLFW, e a metal-cpp serve un ponte: l'API C restituisce oggetti texture di Objective-C, che converti in MTL::Texture* in un file Objective-C++, come nel glfw_bridge.mm del progetto di partenza per macOS.

Il layout decide come vengono salvate le immagini dei due occhi.
.dedicated dà una texture per occhio e richiede due render pass.
.layered dà una sola texture array con uno slice per occhio, e ti permette di disegnare entrambi gli occhi in un pass.
Preferisci layered.

Il ciclo dei frame#

Il ciclo segue lo stato del layer: aspetta finché è in pausa, disegna finché è in esecuzione, ed esci quando viene invalidato.

func renderLoop() {
    while true {
        switch layerRenderer.state {
        case .paused:      layerRenderer.waitUntilRunning()
        case .running:     autoreleasepool { renderFrame() }
        case .invalidated: return
        @unknown default:  return
        }
    }
}

Un frame ha due fasi che annunci al sistema.
Nella fase di update esegui tutto ciò che non dipende da dove si trova la testa: animazione, fisica, input.
Poi dormi fino all'ultimo momento ragionevole, chiedi la posa della testa ed entri nella fase di submission, in cui codifichi e fai il commit.
Aspettare conta: più tardi leggi la posa, meno il sistema deve correggere.

func renderFrame() {
    guard let frame = layerRenderer.queryNextFrame() else { return }

    frame.startUpdate()
    scene.update()                                         // nothing here may depend on the head pose
    frame.endUpdate()

    guard let timing = frame.predictTiming() else { return }
    LayerRenderer.Clock().wait(until: timing.optimalInputTime)

    frame.startSubmission()
    for drawable in frame.queryDrawables() {
        // Where will the head be when this frame is shown?
        let time = LayerRenderer.Clock.Instant.epoch
            .duration(to: drawable.frameTiming.presentationTime).timeInterval
        let anchor = worldTracking.queryDeviceAnchor(atTimestamp: time)
        drawable.deviceAnchor = anchor

        guard let commandBuffer = commandQueue.makeCommandBuffer() else { continue }
        draw(drawable, anchor: anchor, commandBuffer: commandBuffer)
        drawable.encodePresent(commandBuffer: commandBuffer)
        commandBuffer.commit()
    }
    frame.endSubmission()
}

Con l'API C lo stesso frame si legge così.
Ogni chiamata corrisponde uno a uno a un metodo Swift.

void Engine::renderFrame() {
    cp_frame_t frame = cp_layer_renderer_query_next_frame(layerRenderer);
    if (frame == nullptr) { return; }

    cp_frame_timing_t timing = cp_frame_predict_timing(frame);
    if (timing == nullptr) { return; }

    cp_frame_start_update(frame);
    scene.update();                                        // nothing here may depend on the head pose
    cp_frame_end_update(frame);

    cp_time_wait_until(cp_frame_timing_get_optimal_input_time(timing));

    cp_frame_start_submission(frame);
    cp_drawable_array_t drawables = cp_frame_query_drawables(frame);
    for (size_t i = 0; i < cp_drawable_array_get_count(drawables); i++) {
        cp_drawable_t drawable = cp_drawable_array_get_drawable(drawables, i);

        // Where will the head be when this frame is shown?
        cp_frame_timing_t drawableTiming = cp_drawable_get_frame_timing(drawable);
        CFTimeInterval time = cp_time_to_cf_time_interval(cp_frame_timing_get_presentation_time(drawableTiming));
        ar_device_anchor_t anchor = ar_device_anchor_create();
        ar_world_tracking_provider_query_device_anchor_at_timestamp(worldTracking, time, anchor);
        cp_drawable_set_device_anchor(drawable, anchor);

        drawAndPresent(drawable, anchor);                  // encode, cp_drawable_encode_present, commit
    }
    cp_frame_end_submission(frame);
}

worldTracking è un WorldTrackingProvider di ARKit che avvii una volta con ARKitSession().run([worldTracking]).
Impostare deviceAnchor sul drawable dice al sistema per quale posa hai disegnato, così può correggere la differenza.

Due occhi, due matrici#

Ogni drawable ha un elenco di viste, di norma due.
Una vista dà la trasformazione dell'occhio rispetto al dispositivo, e il drawable calcola la proiezione dell'occhio.
Entrambe sono diverse per ciascun occhio, e la proiezione non è simmetrica, quindi non costruirla da un campo visivo.

let deviceTransform = anchor?.originFromAnchorTransform ?? matrix_identity_float4x4

var uniforms = [ViewUniforms]()
for (index, view) in drawable.views.enumerated() {
    let eyeToWorld = deviceTransform * view.transform
    uniforms.append(ViewUniforms(
        view: eyeToWorld.inverse,
        projection: drawable.computeProjection(viewIndex: index)))
}

In C++ leggi gli stessi valori con cp_drawable_get_view, cp_view_get_transform e cp_drawable_compute_projection, e la trasformazione del dispositivo con ar_anchor_get_origin_from_anchor_transform.
La matrice view è simd_inverse(simd_mul(deviceTransform, eyeTransform)).

visionOS usa il reverse-Z: la proiezione manda il near plane alla profondità 1 e il far plane a 0.
Pulisci la profondità a 0 e confronta con .greater.
Le unità sono metri, e l'origine sta sul pavimento nel punto in cui lo spazio è stato aperto.

Entrambi gli occhi in un pass#

Con il layout layered il render pass disegna su una texture array.
La vertex amplification esegue la vertex function una volta per occhio per ogni draw call e instrada ogni risultato verso il suo slice, così la scena viene codificata una volta sola.

let pass = MTLRenderPassDescriptor()
pass.colorAttachments[0].texture = drawable.colorTextures[0]
pass.colorAttachments[0].loadAction = .clear
pass.colorAttachments[0].storeAction = .store
pass.depthAttachment.texture = drawable.depthTextures[0]
pass.depthAttachment.loadAction = .clear
pass.depthAttachment.clearDepth = 0                        // reverse-Z: 0 is far
pass.depthAttachment.storeAction = .store                  // the system needs the depth to reproject
pass.renderTargetArrayLength = drawable.views.count
pass.rasterizationRateMap = drawable.rasterizationRateMaps.first     // foveation

let encoder = commandBuffer.makeRenderCommandEncoder(descriptor: pass)!
encoder.setViewports(drawable.views.map { $0.textureMap.viewport })

var mappings = (0..<drawable.views.count).map {
    MTLVertexAmplificationViewMapping(viewportArrayIndexOffset: UInt32($0),
                                      renderTargetArrayIndexOffset: UInt32($0))
}
encoder.setVertexAmplificationCount(drawable.views.count, viewMappings: &mappings)
encoder.setVertexBytes(uniforms, length: MemoryLayout<ViewUniforms>.stride * uniforms.count, index: 1)

Con metal-cpp il render pass si costruisce allo stesso modo, a partire da cp_drawable_get_color_texture(drawable, 0), cp_drawable_get_depth_texture(drawable, 0), cp_drawable_get_view_count(drawable) e cp_drawable_get_rasterization_rate_map(drawable, 0).
Poi chiama encoder->setViewports, encoder->setVertexAmplificationCount(count, mappings) e collega l'array di uniform per occhio.

Al pipeline descriptor serve maxVertexAmplificationCount = 2, e la vertex function sceglie le sue matrici con l'indice di amplificazione.

struct ViewUniforms {
    float4x4 view;
    float4x4 projection;
};

vertex VertexOut vertex_main(VertexIn in [[stage_in]],
                             ushort eye [[amplification_id]],
                             constant ViewUniforms *views [[buffer(1)]],
                             constant ModelUniforms &model [[buffer(2)]]) {
    VertexOut out;
    float4 world = model.matrix * float4(in.position, 1.0);
    out.position = views[eye].projection * views[eye].view * world;
    out.worldPosition = world.xyz;
    return out;
}

Nota che cosa viene salvato: a differenza del Mac, l'attachment di profondità usa .store, perché il compositor lo legge.
È l'unico punto in cui il consiglio del capitolo sulle GPU tile-based non vale.

Note pratiche#

  • Foveation e post-processing.
    Con una rasterization rate map la texture non è uniforme, quindi un pass a tutto schermo che la legge deve convertire le coordinate attraverso la mappa.
    Comincia senza post-processing.
  • Passthrough.
    Per l'immersione mista, in cui i tuoi contenuti compaiono nella stanza della persona, pulisci a nero trasparente e scrivi alpha premoltiplicato; il sistema compone dietro di te l'immagine delle videocamere.
  • Input.
    Non ci sono né tasti né mouse.
    Pizzichi e sguardi arrivano come eventi spaziali sul layer renderer, e le mani attraverso l'hand tracking di ARKit.
  • Il Simulatore non supporta tutti i layout né la foveation.
    Controlla le capacità invece di darle per scontate, come fa la configurazione qui sopra.
  • Budget.
    Due viste ad alta risoluzione e a 90 Hz lasciano pochi millisecondi di tempo di GPU.
    La scelta consueta è il forward rendering con MSAA, pochi pass e shader a mezza precisione.

Esercizi#

  • Disegna la scena dei dieci cubi di Per iniziare due metri davanti alla posizione di partenza.
    Mostra la soluzione

    Le unità sono metri e l'origine sta sul pavimento, con -z davanti alla direzione di partenza.
    Riduci la scala delle posizioni dei cubi, perché la scena originale si estende per diverse unità, e portali all'altezza degli occhi: una matrice model fatta di una traslazione (0, 1.4, -2) per una scala di 0.25, applicata prima della trasformazione propria di ogni cubo.
    Usa le matrici view e projection per occhio al posto di quelle della camera.

  • Dai a ogni occhio un colore di sfondo diverso e verifica che gli strati siano instradati correttamente.
    Mostra la soluzione

    Con un solo pass e una texture a strati non puoi pulire gli slice con colori diversi, quindi colora nella fragment function: passa l'indice di amplificazione dalla vertex function come valore flat e moltiplica il colore per rosso se vale 0 e per blu se vale 1.
    Se entrambi gli occhi mostrano la stessa tinta, le view mapping sono sbagliate, di solito per un renderTargetArrayIndexOffset rimasto a 0.

  • Passa al layout dedicated e disegna con due pass.
    Confronta il tempo di CPU della codifica.
    Mostra la soluzione

    Imposta configuration.layout = .dedicated.
    Ogni occhio ha allora la sua texture: drawable.colorTextures[i] e drawable.depthTextures[i].
    Crea due render pass descriptor senza renderTargetArrayLength e codifica l'intera scena due volte, ciascuna con le matrici di un occhio e senza vertex amplification.
    L'immagine è identica, e il tempo di codifica sulla CPU circa raddoppia: è ciò che il layout layered fa risparmiare.
